**整屏一条左缘补完 + 开屏卡居中与版面收口**（M10 批11/批12，两批同一张冷启动实拍判出来的账，合并落库）：

- **底部 chrome 走同一对边距**：批10 对齐了四张卡，漏了最底下两行——状态栏与快捷键条从第 0 列起、卡片从第 2 列起，快捷键条第一项还贴窗口边被切。两行改走 `CHROME_PAD_COLS` 同一内衬，仪表 hover 命中区随之平移（`statusZone.gaugeEnd` 加内衬才是绝对列）。
- **反色 run 里不放非 ASCII 字形**：真机对照出来的——卡片"模式"行右边框漂出 3 格，唯一差异是 `•`(U+2022) 落在**反色 run 内部**；SGR 7 会换终端的字体回落，字形的实际推进宽度不再由我们的宽度表做主（离线算宽全对、真机错位，只有两张帧差分对比才找得到）。分段控件三通道改成：颜色=已生效、反色胶囊=光标、尾注=Enter 会不会改变，卡内不再出现夹在反色段里的非 ASCII 字形。
- **开屏卡垂直居中**：`anchorHistory` 三态 `'tail' | 'center' | 'none'`——转录里只剩那张 welcome 卡片时走 `center`（富余空白对半分，落不下去的一格沉在下面），首条消息落地即并回 `tail`，上滚后 `none`。"空白落在顶缘读作上面还有历史"那条判语的前提是**上面真的有历史**；冷启动没有历史，30 行终端里 18 行顶缘空白就只是 18 行空。落点由"转录里只剩一块"推导，不新增可变标志（`store.welcomeCenter` 删除后没有以第二份真相的形式回来）。
- **模式分段控件三格等宽**：`普通`/`混合` 4 列、`PTC` 3 列，原先只有光标格补空格，三格长短不齐像手抖。现在标签补到同一格宽、分隔符两侧留气口；卡片宽按"光标位在架的三种形态与塌缩形态里最宽的那个"量，选择器收起时右边框不横跳（居中时那一跳会整块左右挪）。
- **键名只印键盘上真有的字面**：快捷键条里的 `⏎`(U+23CE) 与 `⌫`(U+232B) 换回 `Enter` / `Backspace`——批7b 立过"字形必须经真机探针选定"的规矩，这两个是漏网的，走终端字体回落时宽度不由我们的表做主；键位提示渲染成豆腐块就是骗人。
- **光标格与占位文本之间留一格气口**：`composerZone` 的注释一直写着"hint one column over"，代码里却没有那个空格。
- **上下文仪表 0 格时整字段降级**：百万窗口开局 13k 用量在 8~16 格里画不出任何一格，整条 bar 只剩纯 `░` 底纹——说的是"什么还不知道"，读起来是噪声。按状态栏既有的"整字段降级、绝不词中截断"规矩丢掉 bar，让 `已用/总量 · 百分比` 自己说话；悬停换形同理，让格会让掉最后一格时不换（宽度守恒不变）。

**破坏面**：`HistoryAnchor` 由 `'welcome' | 'tail' | 'none'` 变 `'tail' | 'center' | 'none'`（公共导出）；`TuiStore.welcomeCenter` 字段删除；`contextGaugeForms` 三档形态在 0 格用量下不含 bar；`buildWelcome` 卡片宽在选择器塌缩后保持不变（原先会窄 2 格）；快捷键条键面文案与底部两行的起始列变更。

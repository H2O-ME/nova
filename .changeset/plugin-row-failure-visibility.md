插件行的失败原因现在**到处可见**（此前「数据在、呈现缺」）：

- **启动不再是无声剔除**。`nova --repl`（含非 TTY 回落）与 `nova exec` 在起跑前逐行念出每一个失败行——点名**行 id + 失败原因**，一行一个，不合并、不截到第一个；失败**不阻断启动**（`exec` 的人类面写在任务回显之前，`--json` 面走既有的 `notice` 控制行）。此前横幅的「插件」一列只列贡献了工具的行，于是加载不了的行在那句里无声缺席，stdout/stderr 一个字的原因都没有。
- **`/plugins` 的失败行带上原因**。roster 条目一直有 `error`，但 `/plugins` 的行丢掉了它，于是 `failed` 只是一个没有下一步的字。现在失败行以 ` — <原因>` 收尾，**关着的行不带原因**（健康地关着没有要解释的事）。
- **原因不可注入终端**。行 id 与原因都来自插件界面的数据（模块名、错误信息），输出前统一把控制码点转成可见转义（`\n` → `\\n`、ESC → `\\x1b`），一个 `\r` 再也覆盖不掉已经打印的字，ANSI 序列也不再改变终端状态。覆盖 `repl`（含非 TTY 回落）/ `exec` / `/plugins` 以及 **`nova plugin add|remove|list` 的全部终端输出**——后者的每一行都插进了外部数据（argv 里的包名、手改的 `plugins.entries` 行 id、用户插件根的路径、npm 与插件自己的失败文案），逐段过同一处转义；固定文案不动。
- **`nova qqbot` 的拒绝区分四种成因**：配置里没有这一行 / 有但 `enabled: false` / 行开着但**模块加载失败**（贴出该行的 `error`）/ 行正常但凭据没填。此前四种共用一句「请打开这一行」，于是照做过的操作者被叫去再做一遍，而真实成因是模块加载失败。
- `AgentSurfaceKernel` 增 `roster()`（结构性镜像 `AgentSurfacePluginRow`）：surface 只对 core 类型，却必须能如实回答「我依赖的那一行现在是什么状态」——四种成因的判定据此**按行 id 通用实现**，宿主不认识任何插件名（`cli/src/plugin-report.ts`）。

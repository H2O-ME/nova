QQ 通道两处「按设计写的、但设计本身不对」的行为，都是用户在真机上直接感到的噪音。

**删掉 `qqbot_send` 工具（`tool.ts` / `plugin.ts` / `outbox.ts`）**：这个通道是**人与 nova 对话**的入口，而模型的话本来就由通道自己送回聊天窗——结论经 `PeerTurns.run` 返回、由 reply 座位落地。更要紧的是工具注册进的是**全局**工具表，于是浏览器与 `exec` 会话里也躺着 `qqbot_send`：一个在浏览器里毫无意义、在 QQ 会话里又与自动回复重复的工具。而它唯一独有的能力（发给**另一个**对端）从来不可用——没有任何地方把 `peerId`（`group:<openid>` / `c2c:<openid>`）告诉模型，模型只能凭空编一个，`outbox` 会因没有该对端的活窗口而拒绝。`tool.ts` 整份删除，`outbox.proactive()` 与早已无人调用的 `outboxNotifier()` 一并删除（留着就是「只写不读」），插件不再 `inject` 工具表、不再注册任何工具。

**删掉「收到，开始处理」回执（`progress.ts` / `turn.ts` / `peers.ts`）**：`accepted()` 此前**无条件立刻**发一句回执，于是每一条入站消息都换来两条回复（回执 + 结论），而读者从这句里学不到任何东西。中途曾把它**延迟**到一个间隔（4s）之后，但一轮 LLM 回答通常就超过 4 秒，所以延迟版在真机上**仍然每条都发**——延迟不是解，删除才是。现在旁白**只由工具调用驱动**：快轮次只花一条消息（结论），慢轮次听到的是**工作本身**（「正在：bash、grep」，每间隔合并成一行）。`TurnObserver.accepted` 这个缝随回执一起删除（留着就是死缝），`ProgressRelay` 不再需要计时器与 `dispose()`。

同轮修了同一族的第二处：`lastSentAt` 初值为 `0`，而任何真实时钟都远大于 0，于是**第一次进展刷新根本不受节流**——一个用工具的两秒轮次会在同一个窗口里再挤进一条「正在：…」。现在它以构造时刻为基线，第一次进展同样等满一个间隔。`final('')` 的「（本轮没有要说的文本，工作已完成。）」改为**无条件**发出：它现在是「一条消息至少换来一条回复」的兜底，而此前它依赖回执必然发过。

直测：`qqbot/test/bindings.test.ts`（结论之前一个字都不发、工具名按间隔合并与节流、首发也等满一个间隔、预算耗尽仍送达结论、无文本轮次有兜底）。变异验证：把 `lastSentAt` 改回 0 / 把回执加回去，两条测试立即变红。

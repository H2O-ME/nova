QQ 通道：**长期绑定**的身份授权、**跨重启存活**的会话绑定、**会话接力**与实时回传。

这个通道有两个部署目标，它们共同决定了这版的形状：**手机遥控桌面的 nova 会话**（远程开发，要求会话接力与实时回传）与**无 GUI 无 WebUI 的云服务器**（openclaw / hermes 式体验，要求连接、授权、对话绑定都持久）。前一版在这两点上都错了，这里一并纠正。

**身份授权（`access.ts`）**。此前 QQ 侧没有任何身份判定：任何人的消息都会进模型，`/perm full` 与 `/approve` 对谁都是通的，而授权用的 `Peer` 只有「往哪回话」——群 id 是每个成员共享的，拿它判定等于判定整个群。

- **`Peer.actorId`**：群里是**成员** openid，私聊是用户 openid；平台没说清是谁时为空，**空身份永不授权**。
- **入网口令长期有效、不被使用消耗**（`pairingCode` 持久在行 config 里，`/pair <码>` 只认私聊）。这是要求而非疏忽：口令用掉一次，第二台设备就再也进不来，而在无 GUI 的服务器上**没有设置页可以再生成一个**。口令在**启动时打印到控制台**（`surface/mode.ts`，经 `runningQqBotAccess()` 读数），那是 headless 部署唯一的凭据通路。撤销是显式动作：设置页 `rotate` / `forget`。
- **权限上限** `maxTier`（默认 `read-only`）在**落地那一步**（`remote.ts` 的 `perm` 分支）判定，超过就把话说出来。缺失 ⇒ 最弱档，绝不是「不限」。
- **唯一入口**：`plugin.ts` 的 `guarded` 同时包住 `brain` 与 `remote.handle`。未绑定的发送者只拿到一句入网提示，**其消息既不进模型、也不建会话**。
- `objectConfig` 支持 `string[]`（`core/src/plugin/schema.ts`）：一个安全相关的**列表**不能存成用分隔符拼起来的字符串——转义会变成操作者的问题，一个多余的分隔符会**悄悄改变谁被授权**。

**会话绑定持久化（`bindings.ts`）**。此前每条消息都为该对端现开一段新会话，于是**一次重启就让每段对话从头开始**——对服务器形态正是最不该有的。现在 `peerId → { kind: 'own' | 'relay', file }` 落在 `~/.nova/qqbot/bindings.json`，**durable 身份是会话日志文件**（内存里的 id 每进程新铸）。三条不变量：已有**活句柄优先**（一份日志不开第二个 writer），没人持有时才按 `resumeFile` 重新投影（这就是重启后续接的机制），`kind` 区分「本对话自己的会话」与「被指到别人的会话上」。写入串行 + 原子（tmp+rename），损坏文档读到「无绑定」而不是猜。

**会话接力（`/sessions` `/use` `/unbind`）**。手机里说的一句要接着桌面正在用的那段会话走。`/sessions` 列活会话（短句柄、工作区末段、是否进行中、是否本对话）；`/use <前几位>` 接上，**歧义一律拒绝**。接力**不抢 `current`**——桌面显示哪一段属于桌面，`activate` 在每轮开始时按绑定发生，于是审计与 job 扇出跟着**正在跑的那一轮**走。

**实时回传（`progress.ts`）**。此前一轮只在结束时说一句话，长任务与挂起无法区分。现在：一条**受理回执**（不计入配额）+ **至多 N 条合并后的进展**（按时间节流，工具名合并成一行）+ **必定送达的结论**。平台不是流——一条外发是绑定某个 `msg_id` 的被动回复且条数有上限——所以配额可以吃掉旁白，**绝不能吃掉结论**；一轮只有工具没有文本时也明说，不留「收到」当最后一句。

**统一 Outbox（`outbox.ts`）**。此前出站有四条各自查窗口、各自发送的路径（入站回复、审批/提问通知、进展、模型自己的 `qqbot_send`），而恰恰那三条规则会咬人：**哪条 `msg_id`**（没有活窗口就必须失败，不能变成平台会限流/拒绝的主动消息）、**一条入站能引出几条回复**（最稀缺的资源）、**配额耗尽时谁赢**。现在账本按 `msg_id` 记且**旁白额度低于总额度**——差额是回复的预留，这就是「结论永不被配额吃掉」的代码落点（一个共享计数器会吃掉回答）。`qqbot_send` 也吃同一个账本：模型自己的外发不能花掉本轮回答的预留。

**提问作答与 `/stop`（`question-reply.ts` / `ask-forward.ts`）**。`canAskUser` 对这个通道改为**真**——问题推到聊天窗（选项编号），对端用 `/answer 2` 选或 `/answer 用 postgres` 作自由文本，多问题按 `id=答案` 分段（散文无法归因，猜就会答错题）。映射是纯函数，因为答错**不会吵闹地失败**：内核按它问过的题校验、不匹配就**拒收**，运行一直停着而对端以为已经答了；没被提到的题**留空跳过**，绝不替对方编；超时按 `cancel`（fail-closed）。审批与提问现在共用同一套「推送 + 必须收敛的定时器」（`ask-forward.ts`），拆成两份就是其中一份迟早没有兜底。`/stop` 与 `/answer` 是**解阻塞**动作，走队列之外的旁路，且 `/stop` 在 abort **之前**读一次 `running`，否则事后分不清「我停掉了」与「本来就没在跑」。

**直测**：`access.test.ts`（9 条，含口令不被消耗、可多设备先后入网）、`bindings.test.ts`（8 条：跨重启读回、损坏文档、并发写、`relay` kind 往返、传输失败被吸收）、`outbox-answers.test.ts`（12 条：无窗口拒绝、旁白额度用尽仍送达结论、平台上限、按窗口计额、题号映射到标签、散文回落、跳过未提及、`/stop` 与 `/answer` 走旁路）。变异验证：群里接受口令 / 绑定只存内存 / 配额吃掉结论 / 旁白吃掉预留 / 无窗口也发 / 题号不映射到标签 / 替对方编答案，逐一变红。
